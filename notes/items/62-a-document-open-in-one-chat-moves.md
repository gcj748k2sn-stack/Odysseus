# 62. A document open in one chat moves into whichever chat you send from next

Open item, moved here from `notes/todo.md` on 2026-10-07 so the dashboard stays short. Its row in the [todo.md](../todo.md) index carries the current status; this file is the full record.

**Seen 2026-10-05 23:31 and 23:38 while testing item 60** (reported as "item 45 popped up again"). The *Pink Oyster Mushroom Growth Phases* document (`68647d12`, created 07-30) was open in the editor. At 23:31 a message from chat `cdb89980` moved it there from `8d72d72f`; at 23:38 the first message of a **New Chat** (`eb49d3d8`, *"read data/settings.json"*) moved it again. `app.db` now has it in `eb49d3d8`; `cdb89980` has no documents left, and the rebind bumped its `updated_at` to 23:38 although the content did not change.
- **Mechanism, from code and log.** `static/js/chat.js` sends `active_doc_id = documentModule.getCurrentDocId()` — the editor's `activeDocId`, whatever chat it came from. **New Chat** (`createDirectChat` in `static/js/sessions.js`) calls `closePanel()` with the comment *"new chat has no docs"*, but `closePanel()` only hides the panel (it even keeps the id as `_minimizedDocId`); `activeDocId` stays set. The server (`routes/chat_routes.py`, grep `cross-session active_doc_id`) owner-checks the id, then **rebinds the document to the sending chat** — *"so future turns find it via the session-fallback path too"* — on the stated assumption that *"the frontend only sends active_doc_id for docs currently visible in the UI"*. After New Chat that assumption is false.
- **Not a context leak this time:** both 23:35 and 23:38 turns had `active_doc_relevant=False`, the document was not put in the prompt (identical `prompt_tokens=7851` with and without it). The damage is the move: the document leaves the chat it belonged to, and the chat it lands in now finds it through item 45's session fallback on later turns.
- **Scope:** 11 `cross-session` rebinds in `app.log*` since 2026-07-14, 3 of them on 10-04/10-05. Which were wanted (the email-draft case the code comment describes) is not established.
- **Answers item 45's open question** (*"whether this ever crosses into a genuinely NEW chat"*): yes — through the explicit-id path, not the fallbacks (#45↔#62).
- **Fix candidates, both XS:** (a) **server**: use a cross-session document for this turn but do **not** rebind it (keep `session_id`, log only) — the email-draft case keeps working, nothing moves; (b) **frontend**: New Chat clears the editor's current document, not only the panel. (a) is testable in Python; (b) needs a live check. **Observable:** after New Chat, the first message logs `active_doc_id=''`; a deliberate cross-chat send logs the mismatch and the document's `session_id` and `updated_at` are unchanged.
