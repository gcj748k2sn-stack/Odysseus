# 52. Odysseus's own notices are replayed to the model as its words

Open item, moved here from `notes/todo.md` on 2026-10-07 so the dashboard stays short. Its row in the [todo.md](../todo.md) index carries the current status; this file is the full record.

---

**Found 2026-10-04 while looking at why models "remember" earlier greetings (sessions `0829a3d2` *"oh"*, `717636da` *"hi mark"*).** The end-of-turn guards in `src/agent_loop.py` append notices to the saved reply — `_empty_response_fallback`'s *"The model returned an empty response…"*, `_stream_failure_notice`, `_gathering_only_notice`, `_unstarted_promise_notice`, `_tool_payload_as_text_notice`. `Session.get_context_messages` replayed them to the model verbatim on every later turn.

- **Measured over `app.db` (copy 2026-10-04 ~20:30, 268 assistant replies, 2026-07-17 → 10-04):** 56 replies carry a notice (empty response 9, stream failure 12, gathering-only 44 — some carry two); **48 were followed by more turns**, so the model read them back.
- **Why it hurts, three ways:**
  - The notices are written for the reader of the transcript: *"the tool results above are real"* points at tool cards only the UI shows. Only reply text is kept for the model, never tool output.
  - **"Ask me to continue" never worked: after a notice, "continue" carried the work on in 0 of 6 recorded cases** — 4 produced another notice, 2 declared the work done or asked what to do (`c1af9e2f` 21:39 thinking: *"nothing was created or changed, I should ask the user"*). Nothing gathered was kept, so there was nothing to continue from.
  - Models reason about the failures as conversation: `0829a3d2` 15:50 thinking — *"Then there's a failure message about model connection."*
- **Built 2026-10-04 (sandbox only).** `src/ui_notices.py` (new): one lexical pattern per template (CLAUDE.md §3 — fixed templates, not model output). `core/models.py` `get_context_messages` now gives the model each assistant reply with notices removed and one neutral line, *"(This turn ended without a complete answer.)"*, in their place — after the model's own text, or alone. Kept rather than dropped: without it a reply ending *"I'll search for…"* reads as if the search happened, and a dropped reply leaves two user turns in a row, which some chat templates reject. User messages and the raw history (what the UI renders) are untouched — the same split as slash-command replies. `_gathering_only_notice` no longer promises *"Ask me to continue"*; it now says *"The results were not kept, so send the request again to rerun it."* The old tail stays matchable for saved chats.
  - **Read-time, not write-time.** The approved plan said to store notices apart from the reply. Stripping on read covers every saved chat as well as new ones with one mechanism; a metadata field would only cover new turns. The cost is that the patterns must track the templates — `tests/test_ui_notices_context.py` builds every notice through the real function, so a wording change fails a test.
  - **Also affects** every other reader of `get_context_messages`: memory and skill extraction, session fork/handoff tools, the context-size estimate in the header. All of them should not have been reading the notices either.
- **Tests:** `tests/test_ui_notices_context.py` (29). **Mutations, each against that file:** wiring removed from `get_context_messages` → 1 fails; stream-failure pattern deleted → 7; a greedy `.*nothing was created or changed.*` pattern added → 6 (negative controls); old *"continue"* tail restored in `agent_loop.py` → 1; stripping applied to user messages too → 1; marker dropped → 9.
- **Corpus check (same `app.db` copy):** 56 of 56 notice-bearing replies changed, **0 residual notice text, 0 of the other 212 replies touched**; 39 became the marker alone, 17 kept the model's own text plus the marker.
