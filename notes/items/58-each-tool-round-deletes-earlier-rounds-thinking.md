# 58. Each tool round deletes earlier rounds' thinking, breaking the prompt prefix

Open item, moved here from `notes/todo.md` on 2026-10-07 so the dashboard stays short. Its row in the [todo.md](../todo.md) index carries the current status; this file is the full record.

---

**Found 2026-10-04 reading the Bonsai 2 chat template against `src/agent_loop.py`. Hypothesis — fits the timings, not measured.**

- **Mechanism.** `_append_tool_results` (`src/agent_loop.py` ~3573) pops `reasoning_content` from *every* earlier assistant message, then appends the new round's assistant message with its reasoning. So round N's request carries reasoning only on round N−1. The Bonsai 2 template (and Qwen 3.5's) renders every assistant message as `<think>\n{reasoning}\n</think>` when `preserve_thinking` is unset — so round N−1's assistant message is rendered **with** its thinking in request N and **without** it in request N+1. The prefix diverges there, and llama.cpp / LM Studio re-read everything after it: that round's tool results and all later ones.
- **Timings that fit (session `cdb89980`, Bonsai 2, ~70 tok/s prefill, 2026-10-04 20:00–20:07):** round 2 (5,364 tok) 47 s — new text only ≈ 2.8k; round 3 (9,028) 127 s — consistent with re-reading ≈ 6.5k; round 4 (12,008) 235 s. Decode time (thinking) is mixed in, so this does not separate the two causes.
- **Side effect, already known for Ollama:** an earlier round rendered as `<think>\n\n</think>` is the *thinking-off* marker for Qwen-family templates; the comment above `_append_tool_results` records Qwen 3.5 drafting its answer inside the think block in 11 of 12 replays when that happened on Ollama.
- **The server says the same:** llama-server logs *"chat template supports preserving reasoning, consider enabling it via --reasoning-preserve"* at startup.
- **Fix candidate:** keep `reasoning_content` on all assistant messages *within the current turn* for llama.cpp / LM Studio endpoints (earlier turns from history have none either way, so the history prefix stays stable). Cost: more prompt tokens per round (the thinking is re-sent), which matters at 16–32k windows — item 50's in-turn overflow gets closer. Measure both.
- ✅ **Clean evidence, 2026-10-04 23:09–23:14** (session `2e9f541d`, Bonsai 2, 32k, q4 KV + bias, `reasoning_effort` medium, `--ctx-checkpoints 32 --cache-ram 2048`, 29 tools, tiny tool outputs). Time to first event per round, against Odysseus's prompt estimate: **r1** 3,204 → 141.5 s (cold, incl. ~29 schemas); **r2** 3,261 (+57) → **1.7 s**; **r3** 3,324 (+63) → **20.7 s**; **r4** 3,496 (+172) → **15.8 s**; **r5** 3,720 (+224) → **18.7 s**. - 🔧 **Built 2026-10-10 (uncommitted): `src/turn_reasoning.py`.** Local endpoints only: at the top of `_trim_route_request_messages` (every request of every round goes through it) each in-turn assistant message gets `reasoning_content` back from `_turn_reasoning`, which `_append_tool_results` never pops. Past 4,000 chars it is shortened to head 1,000 + tail, the same way every time, so the cost is bounded and the prefix stays stable. History messages (no `_turn_reasoning`) and remote endpoints are unchanged, so DeepSeek/Nemotron behaviour (the reason for the popping) is untouched. `estimate_tokens` now counts `reasoning_content`, so trimming sees it. Test through `stream_agent_loop`: each request is an exact prefix of the next, system message included. **Not measured live yet** — the observable is `cache_n` on rounds 3+ in `round_stream_done` (`[prefix-probe]` reads the loop's list, not the request, and will keep naming the old break).
