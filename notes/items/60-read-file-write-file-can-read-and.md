# 60. `read_file` / `write_file` can read and overwrite Odysseus's own secrets

Open item, moved here from `notes/todo.md` on 2026-10-07 so the dashboard stays short. Its row in the [todo.md](../todo.md) index carries the current status; this file is the full record.

---

**Seen 2026-10-05 08:32 and 08:34, session `726f7e32` (Bonsai 2).** Looking for "the last saved data", the model called `read_file` on `/Users/cedrik/odysseus/data/app.db` — `limit 40`, then `offset 1, limit 400`. Both returned `exit_code=0`. The second pushed the next request to **36,656 tokens** (llama-server's count; Odysseus estimated 18,452) against a 32,768 window, so the turn died with HTTP 400.
- 🔀 **Superseded by upstream's fix in the 2026-10-06 merge** ([merge note](../merge-upstream-2026-10-06.md)). Upstream closed the same hole on 2026-09-05 with a containment rule (`_is_app_state_path`: all of `data/` refused except `agent_workspace/`, `uploads/`, `mail-attachments/`, `personal_docs/`, `personal_uploads/`); the filename list below (`_is_odysseus_state_path`) was removed and the test rewritten. **The "still readable on purpose" list below no longer holds** — `memory.json`, `presets.json`, `skills/`, `logs/` are refused now. The `manage_documents` hint survives in upstream's message. The retest below still applies, on the merge branch.
- **Why it is allowed:** `_tool_path_roots()` (`src/tool_execution.py`) makes `DATA_DIR` the **default** root for `read_file`/`write_file`, and `_is_sensitive_path()` only knows home-directory secrets (`.ssh`, `.gnupg`, shell rc files, `.env`, `.netrc`, key filenames). Nothing in `data/` is on it. On this Mac `data/` holds `app.db` (+ two `.bak` copies), `auth.json`, `sessions.json` (7-day session tokens, per THREAT_MODEL.md), `settings.json` (holds `brave_api_key`, `google_pse_key`, `serper_api_key`, `tavily_api_key` keys), `cookbook_state.json`, `scheduled_emails.db`.
- **Relation to THREAT_MODEL.md gap 1** (no sandbox for `bash`): with `bash` in the tool set this adds nothing. Without it — as in this turn, and on every non-Terminus turn — the path check is the only barrier, and its default root is exactly where the secrets live. Read + `web_fetch` is an exfiltration path for prompt-injected web content; `write_file` can overwrite `settings.json` / `auth.json`.
- **Fix candidate (XS):** extend the deny-list for files under `DATA_DIR`: `app.db*`, `*.db`, `*.db-journal`, `*.bak*`, `auth.json`, `sessions.json`, `settings.json`, `cookbook_state.json`, `user_prefs.json` — and tell the model in the error that documents are read with `manage_documents`. Keep `data/uploads`, `personal_docs`, `generated_images` etc. readable. **Test shape:** negative control that `data/uploads/x.txt` still resolves; each listed file rejected for both read and write. **Observable:** the same follow-up turn gets a refusal naming `manage_documents`.
- **Also shown here, item 50's in-turn half:** the round-7 estimate (18,452) was half the real size — binary content tokenizes far worse than text — and nothing checks the size between rounds.
- 🔧 **Fixed 2026-10-05 09:10, commit `0a989557`.** `src/tool_execution.py`: `_is_odysseus_state_path()` refuses, under `DATA_DIR` (case-folded containment), **top-level** `.app_key`, `.key`, `auth.json`, `sessions.json`, `settings.json`, `cookbook_state.json`, `user_prefs.json` and their backup/temp variants (`settings.json.bak`, `auth.json.tmp-…`, `.app_key~`), plus **any SQLite file at any depth** (`*.db`, `*.sqlite*`, `-journal`/`-wal`/`-shm`, `app.db.bak-before-…`, `chroma/chroma.sqlite3`). Both resolvers (default roots and workspace mode) raise *"…is Odysseus's own state … Read documents with manage_documents and memories with manage_memory"*; `_is_sensitive_path()` includes it, so `grep`/`glob` skip those files. **`.app_key` was the worst of it** — the key `src/secret_storage.py` uses for stored email passwords and tokens; it was not in the item's original list.
  - **Second gap found on the way:** `grep`'s **ripgrep branch** never consulted `_is_sensitive_path` — its `--iglob` excludes know only key filenames — so with `rg` installed, `grep` over `data/` printed matching lines from `settings.json` (and from any `.env` rg did not skip as hidden). Its output is now filtered through the same check (`src/agent_tools/filesystem_tools.py`).
  - **Still readable on purpose:** uploads, `personal_docs`, `memory.json`, `presets.json`, `skills/`, `logs/` (checked: no API keys in `app.log*`). A secret *name* below the top level (`uploads/settings.json`) stays readable; a database file anywhere in `data/` does not, including an uploaded `.db` — say so if that bites. **`bash` is still unconfined** (THREAT_MODEL.md gap 1).
  - **Tests:** `tests/test_tool_path_odysseus_state.py` (42) — resolver, workspace mode, `read_file`/`write_file`, `grep` on both branches, `glob`, and one through `execute_tool_block` as admin. **On HEAD 29 fail and the 13 negative controls pass.** Mutations caught: filters blind to state (4 fail), no backup variants (3), no DB rule (9), case-sensitive containment (2), ripgrep unfiltered (1), secret names at any depth (1). **Live check:** ask the agent to *"read data/settings.json"* (or repeat 08:11's *"Use last saved data"*) → refusal naming `manage_documents`, no overflow.
- ⚠️ **Live attempt 2026-10-05 23:35 and 23:38 did not test the fix.** *"read data/settings.json"* classified as `domains=['ui']` ("settings"), so `read_file` was never offered: run 1 answered *"I don't have a file-read tool"*, run 2 tried `web_fetch` on `file:///data/settings.json` and `data/settings.json` (both refused, non-http). Nothing was read.
  - **Retest without risking a leak:** *"read the file /Users/cedrik/odysseus/data/settings.json.bak"* — `files` domain, so `read_file` is offered; the path is blocked by name and **does not exist**, so the refusal shows and nothing can be printed.
  - ⚠️ **Do not retest on the real `settings.json`:** the `files` domain also hands over `bash` (`_DOMAIN_TOOL_MAP["files"]`), and a model refused by `read_file` can `cat` the file — the block only holds on turns without the shell (THREAT_MODEL.md gap 1). That makes "refuse in `read_file`, offer `bash` next to it" the remaining hole for this item; closing it needs a `bash` policy, not a path check.
- 🔴 **That hole was used live on 2026-10-06, on the merged code (Bonsai 2).** *"read the file data/settings.json"* (11:10): `read_file` refused (11:13:28, upstream's containment rule). In the next round the model called `bash` `cat data/settings.json 2>&1 | head -100`. The approval card was shown (11:14:11), the maintainer approved it, and it ran (11:16:31, `exit_code=0`). The contents went into chat `8abca026` and a document *"Code (json)"*; **both were deleted 12:05.** Optional: rotate the search API keys held in `settings.json`.
  - **What this proves:** the path rule holds, and the approval card is the **only** barrier on a turn that offers `bash`. The relative path worked, so the shell's working directory is still the repo root, even though upstream moved `$HOME` to `data/agent_workspace/`.
  - **Fix candidates, not built:**
    - Refuse `bash` commands that name a path under `DATA_DIR` outside the readable subdirectories. That's a lexical check: catches the honest case, not an obfuscated one.
    - Run `bash` with its cwd in `data/agent_workspace/`.
    - Have the approval card warn when the command touches `data/`.
  - **Check:** the same prompt must not end in `cat` succeeding without a warning. Negative control: `ls data/uploads` still runs.

- ✅ **CLOSED 2026-10-07 — accepted, not further fixed (maintainer's decision).** Why it is safe enough now, each point checked that day:
  - **The file tools hold.** Upstream's `_is_app_state_path` (the merge of 2026-10-06) refuses everything under `DATA_DIR` except the readable subfolders, in both resolvers; `grep` from a workspace at the repo root does not print a planted `data/settings.json` (ripgrep and fallback), and `grep path=data` is refused.
  - **`bash` is the only remaining route, and it has two gates:** the *Shell Access* button (`#bash-toggle-btn`) sends `allow_bash=false`, and `routes/chat_routes.py` then removes `bash` from the turn; with it on, every command still needs an approval card.
  - **Nothing secret is stored:** `settings.json`'s four search keys are empty, no email accounts, no model endpoint with an API key, the Cookbook remote-server key empty. Left: `auth.json` (bcrypt hash), `sessions.json` (login tokens) and `.app_key` (protects nothing while no secrets are stored) — the app binds 127.0.0.1.
- **Reopen if any of these changes:** an API key, email account or keyed endpoint is added; the shell is left on routinely; the app is exposed beyond localhost. The fix options above still apply then.
- **Ways the button can be bypassed, recorded so they are not rediscovered:** (1) in **chat mode**, a message classified as a shell/workspace request is auto-escalated to agent mode with `allow_bash = "true"` regardless of the button (`chat_routes.py`, *chat→agent auto-escalation*; none logged since 2026-10-06); (2) a message naming an absolute path outside `data/` binds a workspace and sets `allow_bash = "true"` (paths inside `data/` cannot bind — `vet_workspace` refuses them); (3) the model's `ui_control` tool can switch the button on (`toggle_name: "bash"`), effective from the next message and visible in the composer. The approval card still applies in all three.
